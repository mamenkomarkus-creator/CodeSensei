## 1. Затримка пресетів

```bash
scripts/eval/measure_preset_latency.sh https://codesensei-d5zi.onrender.com 30 > preset.csv
```

Запити послідовні, пауза 1,2 с (ліміт сервера 60 запитів/хв з IP). Заміряється повний час відповіді з боку клієнта `curl`, тож результат включає мережу від точки вимірювання.

## 2. Затримка і якість код-рев’ю

Набір: [`benchmark.json`](benchmark.json), 10 фрагментів C# (9 із закладеною помилкою, 1 контрольний коректний). Категорії: синтаксис, інкапсуляція, наслідування, абстракція, інтерфейс, логіка.

```bash
python3 scripts/eval/run_review_benchmark.py \
  --base https://codesensei-d5zi.onrender.com \
  --out docs/evaluation/results-YYYY-MM-DD.json --repeats 2
python3 scripts/eval/summarize_review_benchmark.py docs/evaluation/results-YYYY-MM-DD.json
```

Скрипт надсилає фрагмент, опитує inbox раз на секунду і фіксує час до готового рев’ю та текст відповіді. Він витрачає денний бюджет моделі (за формулою сервера близько $0,00025 на запит).

**Метрики.**

| Метрика | Визначення |
| --- | --- |
| Затримка | p50 і p95 часу від `POST /api/code/submit` до появи `completed` в inbox |
| Влучання | частка відповідей, що називають закладену помилку (поле `defect`); оцінка ручна: «так», «частково», «ні» |
| Хибне спрацювання | на контрольному фрагменті відповідь вигадує помилку, якої немає |
| Відповідність формату | ≤ 8 рядків, рядок ≤ 55 символів, без markdown, є секції «Помилки/ООП/Підказка» (рахує `summarize_review_benchmark.py`) |

**Правила оцінювання влучання.** Відповідь зараховується, якщо називає саме закладену причину (наприклад, «`i <= nums.Length` виходить за межі масиву»). Загальна фраза («перевірте цикл») не зараховується. Бажано, щоб влучання оцінювали двоє людей незалежно.

**Відомі обмеження.** n = 10 фрагментів — це демонстраційний, а не репрезентативний набір. Модель `gemini-flash-latest` — рухомий псевдонім, тому результати прив’язують до дати прогону. Сервер не повертає `modelVersion` і кількість токенів, тож точну версію моделі та реальну вартість зараз встановити неможливо (див. розділ 5 документації).

## 3. Юзабіліті (SUS)

Мета: оцінити зручність двокрокового код-рев’ю (код у VR → `/paste`).

- **Учасники:** щонайменше 5 студентів, які раніше не користувалися терміналом. Вказати рівень досвіду з VR та з C#.
- **Завдання:** (1) відкрити тему «Поліморфізм»; (2) надіслати власний фрагмент на код-рев’ю; (3) прочитати відповідь. Фіксувати час виконання і кількість звернень по допомогу.
- **Анкета SUS** (шкала 1–5, «зовсім не згоден» … «повністю згоден»):
  1. Я хотів би користуватися цією системою часто.
  2. Система здалася мені надто складною.
  3. Систему було легко використовувати.
  4. Мені знадобилась би допомога технічного фахівця, щоб користуватися системою.
  5. Різні функції системи добре поєднані між собою.
  6. У системі забагато невідповідностей.
  7. Більшість людей швидко навчаться користуватися системою.
  8. Система виявилась дуже незручною.
  9. Я почувався впевнено, користуючись системою.
  10. Мені довелося багато чому навчитися, перш ніж почати працювати із системою.
- **Підрахунок:** для непарних пунктів `відповідь − 1`, для парних `5 − відповідь`; суму помножити на 2,5. Результат 0–100; близько 68 вважається середнім значенням для SUS (Brooke, 1996).
- **Результати** додавати файлом `sus-YYYY-MM-DD.csv` без персональних даних.
